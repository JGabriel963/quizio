# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Quizio is a personal Kahoot clone with no paywalls. **Read before changing behavior:** `specs/constitution.md` (non-negotiables), `docs/architecture.md` (hexagonal rules), `docs/testing.md`. Docs/specs/UI text are PT-BR; code, tests and commits are English (`specs/glossary.md` maps terms).

## Workflow: Spec-Driven Development

No feature is implemented without an approved spec in `specs/features/NNN-slug/`. Use the project skills in order, waiting for human approval between steps: `/sdd-spec <idea>` → `/sdd-plan NNN` → `/sdd-tasks NNN` → `/sdd-implement NNN [Txx]`. The functional source of truth for rules is `specs/product/kahoot-reference.md` (long — Grep for sections); feature order and the deploy checklist are in `specs/roadmap.md`. Architectural decisions go in `docs/adr/`.

## Commands

```bash
pnpm install              # install (pnpm 12, workspaces required — do not use npm/yarn)
pnpm infra:up             # docker compose: postgres :5432, RustFS (S3) :9000/:9001, Soketi (Pusher) :6001 + bucket setup
pnpm infra:down
pnpm dev                  # all packages in dev (web on http://localhost:3001)
pnpm dev:web              # only the web app
pnpm build                # turbo build
pnpm check                # Biome format + lint, writes fixes
pnpm check-types          # tsc in every package except apps/web (see caveat)
pnpm test                 # unit + component + PGlite repository/auth tests, all packages (no infra needed)
pnpm test:watch           # Vitest watch across all projects from the root
pnpm test:int             # *.int.test.ts adapter tests against the containers (needs infra:up)
pnpm test:e2e             # Playwright (desktop + mobile), reuses/starts the dev server (needs infra:up)
pnpm vitest run <path>    # a single test file or directory
pnpm db:start             # only the postgres service
pnpm db:push              # push schema to the local DB (dev only)
pnpm db:generate          # generate migration SQL into packages/db/src/migrations — commit it with every schema change
pnpm db:migrate           # apply migrations (how production gets its schema; see docs/deploy.md)
pnpm db:studio            # Drizzle Studio
```

Caveats:

- `apps/web` has no `check-types` script because it needs `apps/web/src/routeTree.gen.ts`, which only exists after the dev server has run once. Typecheck it with `pnpm -F web exec tsc --noEmit`.
- First E2E run on a machine: `pnpm -F web exec playwright install chromium`.
- Regenerating the Better Auth schema: the CLI version **must match the installed `better-auth`** (newer CLIs generate a different `account` table). From `apps/web`: `npx auth@<better-auth version> generate --config ../../packages/auth/src/index.ts --output ../../packages/db/src/schema/auth.ts --yes`, then `pnpm db:push`.

## Environment

Env lives in **`apps/web/.env`** (not the repo root; template in `apps/web/.env.example`, defaults match `docker-compose.yml`). `packages/db/drizzle.config.ts` and `packages/storage/scripts/setup-bucket.mjs` load that file explicitly. Server vars are validated at import time by `packages/env/src/server.ts` (t3-env + zod), so a missing var is a startup crash, not a runtime `undefined`:

- `DATABASE_URL`, `BETTER_AUTH_SECRET` (min 32 chars), `BETTER_AUTH_URL` (also the only trusted origin and the CORS origin for uploads)
- `AUTH_SIGN_UP_ENABLED` (default `true`) — instance switch for new creator accounts
- `CLIENT_IP_HEADER` (default `x-forwarded-for`) — header the proxy in front of the app reports the client address in; keys both rate limits (Better Auth sign-in, wrong game PINs). Fine as is on Vercel; on a VPS set the one your proxy controls
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` — optional, both or neither (checked in `packages/auth/src/index.ts`); without them the Google button is hidden
- `STORAGE_*` — S3-protocol object storage (Cloudflare R2 in prod, RustFS locally)
- `PUSHER_*` — Pusher-protocol realtime (Pusher cloud or Soketi); `PUSHER_HOST`/`PUSHER_PORT` only for self-hosted
- `VITE_PUSHER_*` — client half, validated in `packages/env/src/web.ts`

Set `SKIP_ENV_VALIDATION=1` to bypass server validation (e.g. in a build container).

Deploy (`docs/deploy.md`, ADR 0011): the `nitro/vite` plugin in `apps/web/vite.config.ts` emits Vercel functions when built on Vercel and a Node server (`apps/web/.output`, run with `pnpm -F web start`) anywhere else; `NITRO_PRESET=vercel` forces the Vercel output locally. `apps/web/vercel.json` applies pending migrations before the build on production deploys only (previews never migrate), so schema changes must stay compatible with the previously deployed code. Keep the code free of Vercel-only APIs — the app is meant to move to a VPS.

## Architecture

Better-T-Stack monorepo (`bts.jsonc` records the generator config), pnpm workspaces + Turborepo, organized as a **hexagonal modular monolith**. **There is no separate server app** — the API runs inside the TanStack Start app as server routes, deployed to Vercel (serverless: no WebSockets, no in-memory state between requests).

```
apps/web            TanStack Start (React 19 + Vite 8), SSR, port 3001 — driving adapter (UI)
packages/core       domain + application: use cases, ports, in-memory fakes. NO infra imports
packages/api        tRPC routers (driving adapter) + container.ts + composition-root.ts
packages/db         Drizzle schema, repository/query adapters, PGlite test harness
packages/storage    ObjectStorage adapter over the S3 API (R2 / RustFS)
packages/realtime   RealtimePublisher (server, `pusher`) + RealtimeSubscriber port/adapter (client, `pusher-js`)
packages/auth       Better Auth built by createAuth({ db, ... }): email+password, Google, DB-backed rate limit
packages/env        t3-env validated env (server / web entrypoints)
packages/ui         design system: shadcn primitives on @base-ui/react + Tailwind v4, Kahoot look
packages/config     shared tsconfig.base.json
```

Dependency rule — enforce it in every change:

- `packages/core` imports nothing outside itself (no drizzle, pusher, aws-sdk, react, zod, env). Needs something external → define a port in `core/src/<context>/application/ports` (or `core/src/shared/application/ports`) and implement it in an adapter package.
- Core is organized by bounded context: `quiz`, `library`, `game`, `reports`, `media`, `identity` (sign-up rules only), plus `shared` (shared kernel). Each has `domain/`, `application/`, `testing/`. Contexts reference each other by ID; a read model (e.g. `library`'s `LibraryQuizQuery`) may reuse another context's value types but not its functions.
- Use cases are factory functions: `createCreateQuiz({ quizzes, storage, ids, clock })` returns `(input) => Promise<output>`. Business errors extend `DomainError` with a stable `code` (`QUIZ.IN_TRASH`); the tRPC middleware maps `NotFoundError` to `NOT_FOUND`, other domain errors to `BAD_REQUEST`, and exposes `data.domainCode`. Other owners' resources are indistinguishable from missing ones (`requireOwnedQuiz`).
- Character limits use `characterCount` (graphemes) from the shared kernel, both on the server and in forms.
- Adapters take explicit config objects (never read env) and are named `<tech>-<port>.ts`. **Only `packages/api/src/composition-root.ts`** and `packages/auth/src/index.ts` (server) and `apps/web/src/lib/realtime-subscriber.ts` (client) know concrete providers. `container.ts` wires use cases to adapters without env so tests build it from fakes.
- Routers are thin: zod validates input *shape* (enums come from core constants), the session provides identity, a use case does the work. No `db` queries in routers.
- Game state is server-authoritative and persisted (response times measured server-side, no server timers); clients never publish realtime events.

**Workspace packages ship raw TypeScript.** Their `exports` map straight to `./src/*.ts` (import as `@quizio/core/quiz/domain/quiz`) — there is no build step for them, Vite compiles them in place. Never add a `dist` import path or expect `pnpm build` to produce package output.

**Dependency versions are centralized in the pnpm catalog** (`pnpm-workspace.yaml`). Shared deps (react, zod, trpc, better-auth, tailwind, typescript, vitest, testing-library…) are declared as `"catalog:"` in each package.json. When adding a dep that more than one package uses, add it to the catalog and reference `catalog:`; bumping a version means editing the catalog, not each package.

### Request flow

- `apps/web/src/routes/api/trpc/$.ts` mounts the tRPC fetch handler at `/api/trpc`, using `appRouter` and `createContext` from `@quizio/api`.
- `apps/web/src/routes/api/auth/$.ts` mounts `auth.handler` at `/api/auth/*`.
- `packages/api/src/context.ts` resolves the Better Auth session and attaches the lazily-built `container`; `protectedProcedure` (in `packages/api/src/index.ts`) throws `UNAUTHORIZED` when `ctx.session` is null and narrows the type.
- Routers live one file per context in `packages/api/src/routers/` (`auth`, `game`, `library`, `media`, `quiz`, `report`), combined in `routers/index.ts`. `AppRouter` is exported as a type and consumed by the client — no codegen.
- Uploads: `media.requestUpload` returns a presigned PUT URL; the browser uploads straight to storage (bytes never pass through Vercel), then sends the key (`quiz.create` / `quiz.updateDetails` with `cover: { type: "set", key }`).

### Client data layer

`apps/web/src/router.tsx` builds the tRPC client (`httpBatchLink` → `/api/trpc`, `credentials: "include"`, **no transformer — `Date`s arrive as ISO strings**; use the view types in `apps/web/src/lib/api-types.ts`), a QueryClient whose `QueryCache.onError` toasts failures unless the query sets `meta: { suppressErrorToast: true }`, and wires `setupRouterSsrQueryIntegration`. `trpc` and `queryClient` are on the router context. In components use `useTRPC()` from `@/utils/trpc` with TanStack Query. Quiz mutations (with cache invalidation, toasts and the "Desfazer" undo) live in `apps/web/src/lib/quiz-mutations.ts`; domain codes map to Portuguese in `lib/quiz-error-messages.ts`.

Routes: `/login?mode=&redirect=&error=`, `/library?section=recent|drafts|trash&q=` (drafts = never published), `/quizzes/$quizId`, `/creator/$quizId`, `/reports?section=reports|trash&q=`, `/reports/$gameId?tab=&view=&participant=&question=`, `/host/$gameId`, `/join`, `/join/$pin`, `/design-system`. `_auth` only guards the session; `/library`, `/quizzes/$quizId` and the reports sit in the pathless `_auth/_shell` layout (sidebar + top bar), while the editor `/creator/$quizId` is full screen outside it.

Editor (spec 003): the page is one `quiz.editor` query; list changes go through `quiz.questions.*`. Autosave lives in `lib/save-tracker.tsx` (header status, retry, `flush()` before leaving) and `lib/use-debounced-autosave.ts` (800 ms, one request in flight per field); `lib/question-mutations.ts` wires the editor actions to tRPC with optimistic list updates from `lib/editor-cache.ts`. Editor mutations use `networkMode: "always"` so an offline save fails visibly instead of pausing. Question edits (spec 004) are `QuestionChange`s applied by the core's pure `applyQuestionChange` on the server and, optimistically, on the client; every editor write goes through one queue in `question-mutations.ts`, because the server rewrites whole question rows. Incomplete questions come from `questionIssues` (not persisted). `Question` is a union discriminated by `type` (`quiz` | `trueFalse`, spec 005): narrow before reading type-specific fields, and add a type by extending `QUESTION_TYPES`, `blankContent`, `parseStoredContent` and `questionContent` in `core/quiz/domain/question.ts`. A type change is the `QuestionChange` `kind: "type"`; what the question had in the other type is remembered only in the client session (`lib/question-type-change.ts`).

Publishing (spec 006): the header's **Salvar** is `quiz.publish`, not the autosave. It checks every question (`incompleteQuestions`) and the title, then freezes the question list as a `QuizVersion` (table `quiz_version`, ADR 0008); title, description, cover and visibility are not versioned. The live `question` rows stay the working copy. "Alterações não salvas" is `sameQuestionLists(live, version)`: the server stores it as `quiz.hasUnpublishedChanges` on every editor write (`markQuizEdited(deps, quiz, questions)`), and the editor computes its own badge from `publishedQuestions` in the editor query (`publishStateOf` in `lib/editor-cache.ts`). `quiz.discardChanges` rewrites the live list from the version. The save/exit flow (which dialog opens, where it leaves to) lives in `components/editor/quiz-editor.tsx`; handlers that run after a save read `actions.current()`, not the render's `data`.

Question image (spec 007): every question may have `image` (`core/quiz/domain/question-image.ts`): the upload's **key**, a placement (`media` | `background`), a crop and an alt text. It is shared by all types (column `question.image`, not part of `content`) and is part of the playable version. The upload reuses `media.requestUpload` + `lib/upload-file.ts`, then a `QuestionChange` `kind: "image"`; the adjustments are `imagePlacement`, `imageCrop` and `imageAltText`. Questions carry keys only: the editor query returns `imageUrls` (key → public URL), read with `imageUrlOf` from `lib/editor-cache.ts`. The crop is parameters (shape, zoom, x/y as fractions of the free travel), drawn with CSS by `lib/image-crop.ts`; nothing is processed on the server. Image files belong to the quiz: `releaseUnusedImages` deletes one only when no live question and no stored version uses it, so never call `storage.delete` on a question image directly. Storage stays swappable (ADR 0003, "Trocar de provedor"): store keys, never URLs, and never build a URL on the client.

Live game (specs 008 to 014, ADR 0009): `core/game` is its own context and never imports `core/quiz`; it reads a quiz through `PlayableQuizQuery`, and the quiz context reaches it through the `QuizGames` port (wired in `container.ts`). A `Game` is a row (`game`, `game_player`, plus `game_question` and `game_answer` once it starts): no memory, no timers. Load one with `loadGame` (`game/application/game-lifecycle.ts`), which applies the 8-hour deadline; end one with `closeGame`; publish with `publishToGame` (best effort, after the write). Players are anonymous: `playerId` + `secret`, kept by the browser per PIN (`lib/player-session.ts`) and sent to the public `game.join.*` procedures. The store also remembers the last game (`last()`), so `/join` without a PIN offers "Voltar como {apelido}" while the server says that game is still open; `/join/{PIN}` goes straight back in. One public channel per game, `gameChannel(gameId)`, with the events in `game/domain/game-events.ts`; events are hints, so each screen also has a query it refetches (`game.view`, `game.join.session`). What two requests at once could break is decided by the database, never by a read followed by a write: unique indexes for the PIN and for one unended game per quiz (`create() → "taken"`, and `hostGame` ends the other and tries again, so the last request keeps the game) and for nicknames (`add() → "nicknameTaken"`); the 200 players are counted with the insert (`add(player, GAME_MAX_PLAYERS) → "full"`). Wrong PINs are limited per client IP (`AttemptLimiter`, `ctx.clientIp`): the attempt is reserved before the PIN is looked up and released when the PIN is right. Removing a player is for the lobby only (`assertInLobby`). Screens: `/host/$gameId` (under `_auth`, outside the shell) and `/join` + `/join/$pin` (public, one parent route that stays mounted; rendered client-only). Game screens wrap in `GameScreen` (`.dark`); `HostLobby`, `HostStage` and `JoinFlow` take their actions as props and the routes wire tRPC. While the game exists (lobby, game and podium) the host's route makes the browser ask before the tab is closed or reloaded (`useLeaveWarning`).

Question cycle (spec 009): a game in progress has a `GameProgress` (`questionIndex`, `phase`, `phaseStartedAt`; phases `gameIntro` → `questionIntro` → `answering` → `results` → `scoreboard`) and every deadline is `phaseStartedAt` plus the phase's duration, checked on the server's clock (`game/domain/game-progress.ts`). **The host's screen drives the game**: `HostStage` asks `game.advance` with the stage it is showing (`from`), the server checks the deadline (`GAME.STAGE_NOT_DUE` if early, unless `skip` on the answers) and writes with `games.saveIfAt(game, from)`, a conditional update, so a repeated or late request changes nothing. `startGame` copies the playable version's questions into `game_question` as `GameQuestion`s (only filled answers, each with its `shapeIndex`; true/false as two answers) and the game never reads the quiz again. An answer is one `game_answer` row keyed by (game, question, player); `submitAnswer` measures the response time and the correctness on receipt and closes the answers when everybody answered. **The right answer never leaves the server before the results**: `HostGameView` sends `correct: null` and no distribution until then, and players only ever get a `PublicStage` (shapes, and texts only with the option of spec 012) plus their own `answered`/`result`. `stage-changed` carries the `PublicStage` and `answer-count` only the total; the host refetches `game.view` when an event is ahead of its view, and a player's device polls `game.join.session` every 5 s while playing. Countdowns use `useCountdown(remainingMs, receivedAt)`: the server sends the time left, never an instant to compare with the device's clock. A device that asks again about the stage it is showing keeps the reading that ends first (`earliestDeadline`; `useSteadyTimeLeft` on the host's screen), so the bar never jumps back by the time the answer took to arrive.

Scoring and scoreboard (spec 010): an answer's `points` are worked out by `answerPoints` in `submitAnswer` (Kahoot's speed formula in `game/domain/scoring.ts`, per right answer marked in multiple selection) and stored with it; **nothing else is stored**. Totals, streaks, places and the scoreboard are derived from the answers on every read (`game/domain/standings.ts`: `rankPlayers`, `scoreboardOf`, `streakAfter`, `standingOf`; `answers.totalsThrough` and `answers.listByPlayer`). What may be told is always worked out up to `revealedThrough(progress)`: the current question once its results are out, the one before until then, so a total never includes an answer whose result is still hidden. The host gets `stage.scoreboard` only in the `scoreboard` phase (and no question there); a player gets `stage.total` and, in `results` and `scoreboard`, `stage.outcome` (result, points, streak, rank, who is right ahead). Points and places never travel in events.

End of the game and animations (spec 011): the last question's results finish the game (`finished`, no scoreboard); **the podium is not a phase**, it is how a finished game is read. `HostGameView.final` has the full standings and `revealRemainingMs`, and `PlayerSessionView.final` the player's place and total; the reveal (third at 2 s, second at 4 s, first at 7 s, `game/domain/podium.ts`) counts from `endedAt` on the server's clock, so the screens use `useCountdown` and a reload goes on from where it is. A request to advance a finished game answers with the podium instead of failing. "Jogar novamente" is `game.host` again (`usePlayAgain`). Animations are presentation only and nothing waits for them: `GameScreen` wraps every game screen in `GameMotion` (`lib/game-motion.tsx`, reduced motion from `usePrefersReducedMotion`); use the `motion` library for what changes place, leaves the screen or runs in sequence (`host/scoreboard.tsx`, `host/podium.tsx`, the question type that opens `QuestionIntro` for `QUESTION_TYPE_REVEAL_MS` before the question shows) and the CSS keyframes in `globals.css` (`motion-safe:animate-pop-in`, `animate-stage-in`, `animate-bar-grow`) for simple entrances; numbers count with `CountUp` (`lib/count-up.tsx`). What an animation starts from and ends at is a pure function (`lib/scoreboard-animation.ts`, `lib/podium.ts`); the scoreboard gets each row's `previous` place and total and `stage.scoreboardLeavers` from the server. In tests `MotionGlobalConfig.skipAnimations` is on (`src/testing/setup.ts`) and `stubReducedMotion` fakes the preference; a number that counts up needs `waitFor`, or a tick with fake timers.

Game options and joining late (spec 012): a `Game` has `options` (`GameOptions` in `game/domain/game-options.ts`: `showQuestionsOnDevices`, `randomizeQuestions`, `randomizeAnswers`), copied by `hostGame` from the host's saved preferences (`HostPreferencesRepository`, table `host_preferences`) and changed by `game.setOptions`; the lock is not one of them and is never carried to the next game. **Each setting is written on its own**, with `games.saveLocked` and `games.saveOptions` (only the options that changed; `preferences.save` likewise), never with `games.save`, which rewrites the whole row: a setting changed during the game must not undo an advance, and two switches turned at the same time must both be kept. The random orders are drawn once, in `startGame` (`arrangeGameQuestions` with the `Shuffler` port; true/false is never shuffled), so they only change in the lobby (`GAME.OPTIONS_FIXED`). A game in progress takes players: `Player.firstQuestionIndex` (`firstQuestionFor`) is the first question they may answer, `players.countEligible` is who a question waits for, and `PlayerStageView.sittingOut` tells the device to wait for the next question. With `showQuestionsOnDevices`, `publicStageOf(game, question, imageUrlOf)` adds the statement (from the question's intro) and the image and answer texts (from the answers on); never which answer is right. On the host, `GameHeader` opens `GameSettings` (a `Sheet` of `Switch`es) in the lobby and during the game and shows the PIN during the game; on the phone, `AnswerButtons` has three formats (shapes, texts, and marks plus "Enviar" for multiple selection) and `question-on-device.tsx` draws the statement, the image and the time, laid out as in Kahoot: the image takes the top (or the whole screen behind, when the editor set it as background) and the statement, the answers and the time bar sit at the bottom.

Lost connections and ending now (spec 013): a screen has **lost its connection** when a request gets no answer (`isConnectionFailure` in `lib/connection.ts`: no `data` on the error, or the 5 s of `withTimeout`); a refusal is the server answering. `useConnectionWatch({ enabled, probe, onBack })` holds that state for both screens: `report(error)` and the browser's `offline` mark it lost, it retries `probe` every 5 s and comes back by itself. On the host, `ConnectionLostDialog` (an `AlertDialog` that cannot be closed) covers the lobby, the game and the podium; the route keeps the game on the screen when a refetch fails, and `HostStage` takes `connected` so the stage that ran out meanwhile is asked for again on the way back. **The host's presence is a column**: the screen calls `game.signal` every 4 s (`useHostSignal`), `signalHost` writes `game.hostSeenAt` on its own with `games.saveHostSeen` (never `games.save`) and publishes `host-back` only when the host was away; `PlayerSessionView.hostIdleMs` tells each device how long the host has been silent, and 10 s (`HOST_AWAY_AFTER_MS`, `game/domain/host-presence.ts`) is "O anfitrião se desconectou". No event tells that the host left: the device asks its session again when the silence would reach the limit (`nextSessionCheckInMs`). On the phone, `ConnectionBar` shows the device's own trouble first, then the host's, over a darker screen that still takes touches: deadlines keep running and answers keep counting without the host. Its "Sair" (`stepOut`) goes to the PIN without clearing the session, so "Voltar como {apelido}" is offered. An answer that got no reply shows "Sua resposta não foi enviada." and gives the buttons back. "Encerrar agora" is the last line of `GameSettings`, which holds its own `EndGameDialog` so cancelling returns to the panel; a game ended in the middle still has no podium.

Autoplay (spec 014): "Reprodução automática" is one more `GameOptions` switch (`autoplay`, saved with the host's preferences), but it is **a deadline, not another way of moving the game**: with it on, the lobby, the results and the scoreboard get a time, and the host's screen asks when it runs out, as it already does for the timed phases. The game keeps **since when** it is on (`Game.autoplaySince`, column `autoplay_since`, null when off; always `options.autoplay` told another way) and `game/domain/autoplay.ts` works the countdowns out on the server's clock: 15 s (`AUTOPLAY_START_MS`) from the last arrival or from the switch being turned on, whichever is later, and only with somebody in the lobby; 5 s (`AUTOPLAY_ADVANCE_MS`) from the phase's start or the switch. "The last arrival" is `players.lastJoinedAt`, which counts removed players, so removing one among several does not move the countdown. `nextStage` refuses to leave the results or the scoreboard early when autoplay is on (`GAME.STAGE_NOT_DUE`), and `game.start` with `auto` is checked the same way, because a player may join at the last moment; a click on Iniciar is never checked. `changeGameOptions(game, change, now)` and `games.saveOptions(gameId, change, at)` take the instant, and turning on what is already on keeps the first one. The host's view carries `autoStart` and `stage.autoAdvance` (`{ remainingMs, token }`): the token names the countdown, so the screen starts over when it changes (`useSteadyTimeLeft` keyed by it) instead of keeping the reading that ends first. `AutoCountdown` shows it beside Iniciar and in the place of Avançar; players' devices get none of it, and the podium does not start another game. The route refetches the game when a player joins or leaves with autoplay on, and when the switch changes.

Reports (spec 015, ADR 0010): **a report is not stored, it is a reading of a game**. `core/reports` reads the game's rows through its own query port, `ReportGameQuery` (headers for the list, tallies for the list's accuracy, the whole game for an open report), as `library` does with quizzes: it reuses the game's value types and none of its functions. A game is a report when it started (`questionCount > 0`) and is over (`endedAt` set, or past `expiresAt`, in which case it ended at the deadline where it was); every number comes from pure functions over that reading (`reports/domain/report-stats.ts`, `accuracy.ts`). Three rules to keep in mind: only **played questions** count (the ones that reached their results, `playedQuestionCount`, which repeats the game's `revealedThrough`); a participant's questions start at their `firstQuestionIndex`, so a late player is not charged for what came before; and 35% is compared on the two integers of an `Accuracy`, never on the rounded percent (below 35% is a difficult question or a participant who needs help, exactly 35% is not). What is the report's own is the table `report` (name and `trashedAt`), with a row only once it was renamed or trashed, written one column at a time by `ReportRepository`; deleting a report for good deletes the game. **`game.quiz_id` is not a foreign key**: a game that started outlives its quiz, and deleting a quiz for good ends its open games and deletes the ones that never started (`games.deleteUnstartedByQuiz`, called from the container's `quizGames`). Images are still the quiz's, so a report builds their URLs only while `header.quiz` is not null. On the web, `/reports` lists them (search and "Mostrar mais" are the `limit` of `report.list`; the selection is the page's) and `/reports/$gameId` keeps the tab, the list inside it and the open detail in the address (`tab`, `view`, `participant`, `question`); the details open in a `Sheet` and have their own queries. `AccuracyRing` always has its number beside it; labels and formats live in `lib/report-labels.ts`.

Realtime in components: `useRealtimeEvent(channel | null, event, handler)` from `apps/web/src/lib/realtime.tsx`, under the `RealtimeProvider` mounted in `__root.tsx`. The socket opens lazily on first subscription, never during SSR.

### Auth flow

Client-side calls go through `authClient` (`apps/web/src/lib/auth-client.ts`, Better Auth React); `routes/login.tsx` wires them into `components/auth/*` forms, which receive actions as props (testable without Better Auth) and map error codes with `lib/auth-error-messages.ts`. The `_auth` route group (`routes/_auth/route.tsx`) guards its children in `beforeLoad` and redirects to `/login?redirect=<href>`; after signing in, `safeRedirect` only allows internal paths. Server-side, `getUser` (`apps/web/src/functions/get-user.ts`) returns the session. Game players are anonymous (nickname only) and do not use Better Auth sessions.

`packages/auth/src/create-auth.ts` holds all Better Auth options: sign-up rules hook, `disableSignUp` plus a `databaseHooks.user.create.before` guard (closed sign-up on every path), Google with `accountLinking.requireLocalEmailVerified: false` (accepted risk, ADR 0007), and rate limiting stored in the `rate_limit` table (5 attempts/60 s per IP on email sign-in/sign-up, enabled in dev too). Auth tables live in `packages/db/src/schema/auth.ts` and are generated — regenerate (see caveat) rather than hand-editing.

## Testing

TDD is the default (red → green → refactor). Details in `docs/testing.md`.

- Vitest 5, `globals: false` (import `describe/it/expect` from `vitest`); `clearMocks` is on by default. Each package has its own `vitest.config.ts` (`defineProject`); adapters with real-service tests also have `vitest.int.config.ts`.
- Tests sit next to the code: `*.test.ts(x)` for unit/component, `*.int.test.ts` for adapter integration, `apps/web/e2e/*.spec.ts` for Playwright.
- Isolate ports with the in-memory fakes (`packages/core/src/*/testing/*`, `packages/realtime/src/testing/*`), not `vi.fn()`; inject `Clock`/`IdGenerator` instead of `Date.now()`/`crypto.randomUUID()` in core. `aQuiz()` builds test quizzes.
- Router tests: `createTestApi()` from `packages/api/src/testing/test-context.ts` (real routers and use cases over fakes; `callerFor(userId | null)`).
- Repository tests: `createTestDb()` from `packages/db/src/testing/create-test-db.ts` (PGlite + `drizzle-kit/api` pushSchema; no Docker). Repositories accept the driver-agnostic `Database` type from `packages/db/src/types.ts`.
- Auth tests (`packages/auth/src/create-auth.test.ts`) drive the real `auth.handler` over PGlite; Google is exercised through ID-token sign-in with stubbed `verifyIdToken`/`getUserInfo`. Give each client a distinct `x-forwarded-for`, or the per-IP rate limit leaks between tests.
- Web components that render router `Link`s use `renderWithRouter` from `apps/web/src/testing/render-with-router.tsx`.
- E2E helpers are in `apps/web/e2e/support.ts` (`signUp` sets a unique client IP per test for the same rate-limit reason).

## UI conventions

- Design tokens (Kahoot palette, `answer-red/blue/yellow/green`, `brand`, `success`, `shadow-press*`, Montserrat) and `@source` globs live in `packages/ui/src/styles/globals.css`; `apps/web/src/index.css` only re-imports it. There is no `tailwind.config`. Reference: `docs/design-system.md`, live catalog at `/design-system`.
- Shared primitives live in `packages/ui/src/components` and are imported as `@quizio/ui/components/<name>`; app-only components go in `apps/web/src/components` (`auth/`, `editor/`, `game/`, `home/`, `library/`, `quiz/`, `reports/`) and import via the `@/` alias.
- Primitives wrap **`@base-ui/react`**, not Radix (shadcn style `base-lyra`). Match the pattern: `cva` variants + `cn()` (from `@quizio/ui/lib/utils`) + a `data-slot` attribute. **Customize at the root**: new Kahoot-style variants go into the component's `cva` (e.g. `Badge` `private`/`unlisted`), not wrappers. Primitives use `rounded-md` (not lyra's `rounded-none`).
- Answer alternatives: `AnswerOption`/`AnswerShape` — color is derived from shape, fixed order via `answerShapeAt(index)`.
- Add shared primitives from the repo root: `npx shadcn@latest add <component> -c packages/ui` — **it prompts to overwrite existing files such as the customized `button.tsx`; answer no** — then convert the generated file to the project style (imports, tabs, Kahoot look). Run the CLI from `apps/web` only for app-specific blocks.
- The app is light-themed (`<html lang="pt-BR">`); the `.dark` class is reserved for in-game screens. `next-themes` is available but not wired up.
- Links styled as buttons: `<Button render={<Link to="…" />} nativeButton={false}>`.

## Formatting & generated files

Biome (`biome.json`) is the only formatter/linter: **tabs** for indentation, double quotes, import organization on. `useSortedClasses` auto-sorts classes inside `cn`/`clsx`/`cva`. Run `pnpm check` before finishing a change.

`apps/web/src/routeTree.gen.ts` is generated by the TanStack Start Vite plugin and gitignored — never edit it; add a file under `apps/web/src/routes/` and let the dev server regenerate.
